When it happens, run appears to see only the ~25 bundled defaults instead of the full set (~46 = bundled + global + project, including.archon/workflows/experimental/). Observed repeatedly while dogfooding archon-fix-github-issue-experimental / -codex from the Archon repo itself. It is intermittent — the identical command worked on one occasion and saw only 25 workflows on another, and an immediate retry usually succeeds. Failures occurred both with and without --branch, so worktree creation alone is not the discriminator. The affected workflow file is tracked in git (only sibling experimental variants are untracked), and no stale ~/.archon/workspaces/<owner>/<repo>/source/ clone exists (only artifacts/ + worktrees/), ruling out a stale-clone discovery root. Why this is more than an annoyance The bash-dispatcher pattern (a workflow node shelling out to archon workflow run <sub-workflow> --detach to fan out parallel implement tasks — the current workaround while #977 / #1764 are open) makes workflow run discovery a load-bearing dependency of fan-out workflows. An intermittent bundled-only view turns into intermittently failing dispatch nodes. Code seams (where list and run can diverge) Both subcommands resolve effectiveCwd to the git repo root in packages/cli/src/cli.ts:400-408 and call the same discovery: list → workflowListCommand(effectiveCwd) → loadWorkflows(cwd) → discoverWorkflowsWithConfig(cwd, loadConfig) (packages/cli/src/commands/workflow.ts:306-317, 332) run → workflowRunCommand(effectiveCwd,...) → loadWorkflows(options.discoveryCwd?? cwd) (packages/cli/src/commands/workflow.ts:397) So a fresh foreground run should be identical to list. The places where run takes a different discovery root: Resume paths set discoveryCwd from the codebase row — workflow resume / approve / reject re-enter workflowRunCommand(run.working_path,...) and set discoveryCwd = codebase.default_cwd precisely so discovery does NOT happen in the worktree (packages/cli/src/commands/workflow.ts:1430-1463, comment at 1430-1432). The codebase lookup failure is swallowed: if getCodebase throws or returns null, the code WARNs (cli.workflow_resume_codebase_lookup_failed / _not_found) and continues with discoveryCwd = undefined — discovery then silently runs in run.working_path (the worktree), where untracked workflow YAMLs (e.g. experimental variants) don't exist. That is a silent fallback to a degraded discovery root, against the fail-fast rule. Auto-resume makes path 1-2 reachable from a plain run: workflow run silently auto-resumes a prior failed run (/workflow run silently auto-resumes failed runs with stale args, hijacking fresh requests #1549). A user typing workflow run <name> can therefore end up on the resume/worktree discovery path without knowing it — which would also explain the intermittency (it depends on whether a resumable failed run exists at that moment). --detach re-invokes the CLI as a detached child (packages/cli/src/commands/workflow.ts:106) — if the child's argv/cwd reconstruction ever differs from the parent's resolved --cwd, the child discovers from a different root. What needs to happen Reproduce with --verbose and capture which discovery root run actually used (today it isn't printed for the non-resume path — Discovery path: is only logged when discoveryCwd is set, workflow.ts:1453). Logging the effective discovery root + workflow count on every run would make the next occurrence diagnosable. Fix the silent fallback in the resume paths: if run.codebase_id is set but the codebase row can't be loaded, fail loudly (or at minimum surface "discovering from worktree, project workflows may be missing") instead of WARN-and-degrade. Confirm or rule out the /workflow run silently auto-resumes failed runs with stale args, hijacking fresh requests #1549 auto-resume interaction — if confirmed, the fix for /workflow run silently auto-resumes failed runs with stale args, hijacking fresh requests #1549 likely fixes the common case of this bug too. Confirm the --detach child re-invocation preserves the resolved repo-root --cwd. Environment macOS, source build (bun run cli), SQLite, observed on the Archon repo itself (project workflows partly untracked under.archon/workflows/experimental/).
