Any community workflow that bundles command prompts (the common case — workflow YAML references command markdown by name) cannot be installed globally and then run against another repo's worktree. Repro Take a workflow with command nodes — for example the marketplace workflow archon-idea-to-wo (workflow YAML at.archon/workflows/foo.yaml, commands at.archon/commands/foo-step-1.md etc.) "Install" globally by dropping files at: ~/.archon/.archon/workflows/foo.yaml ✅ found ~/.archon/.archon/commands/foo-step-1.md ❌ not found From another repo, run: archon workflow run foo --branch my-feat "..." (worktree mode, branch base does not contain those files) Workflow discovers the YAML from the global path, but the first command node fails immediately: "searchPaths":[".archon/commands",".archon/commands/defaults","app defaults"] "msg":"command_not_found" Workflow exits with anyCompleted: false, anyFailed: true. Root Cause The asymmetry is in the path-resolution helpers: Workflows (packages/workflows/src/workflow-discovery.ts:186-212) — discoverWorkflows() accepts a globalSearchPath option and explicitly searches join(globalSearchPath, '.archon/workflows/'). Logs global_workflows_loaded. Commands (packages/workflows/src/executor-shared.ts:124-245) — loadCommandPrompt() has no global path parameter. Line 158 calls archonPaths.getCommandFolderSearchPaths(configuredFolder) which returns only project-relative paths. Path helper (packages/paths/src/archon-paths.ts:110-123) — getCommandFolderSearchPaths() accepts an optional configuredFolder but no globalSearchPath. Returns only ['.archon/commands', '.archon/commands/defaults', configuredFolder?]. getDefaultCommandsPath() exists at packages/paths/src/archon-paths.ts:190-192 but is only wired into the bundled-defaults layer, not a configurable user-global path. CLI call sites confirming the asymmetry: packages/cli/src/commands/workflow.ts:122-124 — passes globalSearchPath: getArchonHome() for workflows. packages/core/src/orchestrator/orchestrator-agent.ts:384-386 — same pattern for the orchestrator. No equivalent call site exists for command resolution. Impact Any community workflow that bundles command prompts cannot be installed globally — and since command nodes are the primary way to inject domain logic, that's most marketplace workflows. The new marketplace install (PR feat: workflow marketplace v0 — catalog, JSON endpoint, CLI search/install #1624 / auto-review feat: add marketplace PR auto-review and merge workflow #1638) implicitly assumes command resolution will work from the install destination, but it doesn't. Workaround today: commit the workflow + commands to a side branch in the target repo and base the worktree off that branch. Not viable for end-users. Proposed Fix Mirror the workflow pattern: Add optional globalSearchPath?: string parameter to getCommandFolderSearchPaths() in packages/paths/src/archon-paths.ts. Add optional globalSearchPath?: string parameter to loadCommandPrompt() in packages/workflows/src/executor-shared.ts, threaded into the searchPaths array between project paths and bundled defaults. Update callers (packages/workflows/src/dag-executor.ts:751 and others) to thread getArchonHome() through, matching the workflow side. Apply the same fix in packages/workflows/src/validator.ts:131-155 (mirrors the same project-only gap). Related PR feat: workflow marketplace v0 — catalog, JSON endpoint, CLI search/install #1624 — marketplace v0 PR feat: add marketplace PR auto-review and merge workflow #1638 — marketplace auto-review Earlier work that introduced globalSearchPath for workflows but did not extend it to commands (the global_workflows_loaded log line is the marker) Surface Where Discovered While testing archon-idea-to-wo (community workflow being added in PR #1678) end-to-end against the Archon repo on dev. Globally installed the workflow YAML at ~/.archon/.archon/workflows/archon-idea-to-wo.yaml and the four commands at ~/.archon/.archon/commands/archon-wo-*.md. Workflow was discovered (global_workflows_loaded: 1), worktree was created off dev, then the first node failed with command_not_found.
