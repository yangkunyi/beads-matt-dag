project</a> where a coding agent autonomously improves a neural network training script. The agent edits <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">train.py</code>, runs a 5-minute training experiment on a GPU, checks the validation loss, and loops - keeping changes that help, discarding those that don’t. In Karpathy’s <a href="https://xcancel.com/karpathy/status/2031135152349524125#m">first overnight run</a>, the agent found ~20 improvements that stacked up to an 11% reduction in time-to-GPT-2 on the nanochat leaderboard.</p><p>The default setup: one GPU, one agent, one experiment at a time. ~12 experiments per hour. We wanted to see what happens when you remove the infrastructure bottleneck and let the agent manage its own compute.</p><h2 id="how-autoresearch-works" class="group relative mr-auto !ml-0 !max-w-[95%] scroll-mt-28"><a href="#how-autoresearch-works" class="!no-underline"><span>How autoresearch works<!-- --> </span><span class="text-carbon/40 text-18px opacity-0 transition-opacity group-hover:opacity-100">#</span></a></h2><p>The project has three files:</p><ul><li><strong><code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">prepare.py</code></strong> - Downloads data, trains a tokenizer, provides the dataloader and evaluation function. Read-only. The agent cannot touch it.</li><li><strong><code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">train.py</code></strong> - The GPT model, optimizer, and training loop. This is the <em>only</em> file the agent modifies.</li><li><strong><code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">program.md</code></strong> - Instructions for the agent: what it can change, how to evaluate results, when to keep vs. discard changes.</li></ul><p>The constraint is a fixed 5-minute wall-clock training budget. The agent’s job is to minimize <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">val_bpb</code> (validation bits per byte) within that window. Everything in <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">train.py</code> is fair game - architecture, hyperparameters, optimizer settings, batch size, model depth - as long as the code runs without crashing.</p><p>The default setup assumes you have a local GPU. You run <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">uv run train.py</code>, wait 5 minutes, check the result, edit, repeat. The agent automates the edit-run-check loop, but the experiments are still sequential.</p><h2 id="the-bottleneck-one-gpu-one-experiment" class="group relative mr-auto !ml-0 !max-w-[95%] scroll-mt-28"><a href="#the-bottleneck-one-gpu-one-experiment" class="!no-underline"><span>The bottleneck: one GPU, one experiment<!-- --> </span><span class="text-carbon/40 text-18px opacity-0 transition-opacity group-hover:opacity-100">#</span></a></h2><p>Running experiments sequentially means the agent spends most of its time waiting. A typical cycle looks like:</p><ol><li>Agent edits <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">train.py</code> (~30 seconds)</li><li>Training runs (~5 minutes)</li><li>Agent reads the result, plans the next experiment (~30 seconds)</li></ol><p>Steps 1 and 3 are cheap. Step 2 dominates. And during step 2, the agent is idle - it could be preparing the next experiment, or the next ten.</p><p>The bigger problem is combinatorial. Say the agent finds that lower weight decay helps and that a different Adam beta also helps. It wants to try them together. But with sequential execution, testing the combination means waiting another 5 minutes. With 16 GPUs, the agent can test that combination alongside a dozen other ideas simultaneously. Instead of testing one hypothesis per 5-minute window, it tests a factorial grid in a single wave.</p><h2 id="giving-the-agent-cloud-gpus" class="group relative mr-auto !ml-0 !max-w-[95%] scroll-mt-28"><a href="#giving-the-agent-cloud-gpus" class="!no-underline"><span>Giving the agent cloud GPUs<!-- --> </span><span class="text-carbon/40 text-18px opacity-0 transition-opacity group-hover:opacity-100">#</span></a></h2><p>To arm the agent with GPUs, we used <a href="https://skypilot.co/">SkyPilot</a>. It’s an open-source tool that launches jobs across clouds and Kubernetes from a YAML file and includes a <a href="https://docs.skypilot.co/en/latest/getting-started/skill.html">skill</a> that teaches coding agents to use it. The agent reads the skill, then launches and manages GPU clusters on its own - no manual cloud setup.</p><p>Each experiment is defined in a short YAML (<code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">experiment.yaml</code>) that specifies the GPU type, installs dependencies, runs <code class="bg-grey-100 text-15px rounded px-1.5 py-0.5 font-mono text-sky-400">train.py</code>, and prints metrics to stdout.
