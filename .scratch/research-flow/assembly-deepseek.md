# Research: assembling a bottom layer for this repo's already-built product, now with multi-person collaboration

**Repo / cwd:** `/data3/yky/beads-matt-dag` (current Main), read-only for this run (no edits to `docs/`, `tools/`, pack, or the beads store).
**Question:** given everything already decided and built (store = beads, three executors, operator surface = a view with one tagged write door), what does the *complete* assembly need, which existing products/components fill each layer, who owns what under multiplayer, and what should this repo actually assemble?
**Evidence labels:** **direct evidence** = text on a fetched page or in a local file; **interpretation** = what that text implies here; **researcher inference** = my own reasoning, not stated by any source.
**Network limits this run:** `docs.github.com` / `github.com` are blocked from this host (`198.18.0.0/15` TUN/fake-IP); GitHub claims use Wayback snapshots. `source_check` was **unavailable** (Exa 429, and no other search provider has a key configured) — so no machine validation was possible and **every claim below rests on a page or file I fetched directly** unless labelled otherwise. `web_search` was largely unusable for the same reason; discovery of Linear doc URLs came from `linear.app/sitemap.xml` and `linear.app/docs`, and discovery of beads doc pages from `beads.gascity.com/llms.txt`.

---

## Summary

Nothing I fetched replaces beads for this repo: no owner product owns local Dolt + hash ids + `bd ready` + the five triage labels + this repo's crossing rules in one place, and no write the operator surface needs was found missing from beads. Multiplayer does **not** need a new store — it needs (a) a store that tolerates more than one writer, which beads already ships as **server mode** (`bd init --server`, "multi-writer … concurrent writers"), and (b) identity/permission/attribution that beads explicitly does **not** own (assignees are plain strings; the actor/comment author is a free string resolved from `--actor` / `BEADS_ACTOR` / `git config user.name`), so that layer has to live in front of the existing tagged write door. The recommended assembly is therefore **keep beads, keep three executors, keep the one intent door, and grow the door into the multi-human layer** — optionally replacing the DIY React Flow rendering with a community Beads UI, but never its write path, and never the store.

## Findings

### 1. What the complete assembly needs, split three ways

**Claim:** The assembly is three layers with a fixed seam: store primitives (beads), a view that projects them and writes through one door, and execution (three domain runs, untouched by the view). Multiplayer adds requirements in exactly two of them — the store's *writer* posture, and the view's *identity* posture — and adds nothing to execution.
**Sources:** local `docs/CONTEXT.md`, `docs/adr/0001-...md`, `docs/adr/0007-...md`, `docs/specs/2026-09-17-operator-surface.md`, `docs/agents/issue-tracker.md`; local `tools/operator-ui/serve.ts` (read this run). **Support:** direct evidence + interpretation. **Confidence:** high.

| Layer | Already built (must be kept) | What multiplayer adds (new, and where it can live) |
|---|---|---|
| **Store primitives** (beads) | hash id identity + `handle`/`slug` metadata; status `open`/`in_progress`/`closed`; derived blocked/ready (`bd ready`, `bd blocked`, `bd recompute-blocked`); intra-domain `blocks`; crossing `relates-to` / `discovered-from`; flat append comments (`bd comment`, `bd comments`); labels; `bd delete` refusing dependents; `bd history` | *More than one writer*: embedded mode is single-writer (file-locked) — server mode is the store's own answer ("Multi-writer support … server mode enables concurrent writers"). *Per-mutation history with an actor*: the events journal (`bd events tail`, `GET /v0/beads/events`, SSE `events:watch`), off by default, carries `"actor"` per record. *Not owned by the store*: who a human is, sessions, permissions — beads has no user registry |
| **View** (operator-ui, already on Main) | React Flow projection of the store; positions/gestures local; one tagged HTTP intent door (`POST /comment`) refusing `closed`, `reading:`, non-triage labels, cross-domain `blocks`, `parent-child`; start = existing domain run + allow-list | *Identity*: an authenticated human per browser session, stamped into the write (`bd comments add --author`, `--actor`/`BEADS_ACTOR`). *Liveness*: re-read the store without a full reload (poll, or tail the journal / SSE). *Attribution & presence*: who wrote what, who is looking/editing. *Conflict policy*: last-write-wins is the store's default; the door must decide what to do about it |
| **Execution** (three runs) | `beads-dag-drain` (closed = in Main), `beads-dag-inquiry` (closed = question answered), `beads-dag-experiment` (closed = record complete); shared shell; the run lock is the one mutex; workers run `BD_READONLY=1`; allow-list is a claim pool outside the store | **Nothing.** Multiple humans do not multiply executors, and the start path already refuses when the Target run lock is held (spec story 53). A second concurrent run is a run-lock question, not a multiplayer one |

### 2. Beads owns the store primitives, including the two multiplayer-relevant ones (concurrency and per-mutation actor)

**Claim:** Beads ships two storage/writer modes plus a proxied mode, a per-mutation events journal (off by default) and an opt-in audit sidecar; multi-writer is a mode switch, not a schema problem.
**Sources:** [Dolt Backend for Beads](https://beads.gascity.com/architecture/dolt.md) → "**Multi-writer support** — server mode enables concurrent agents"; embedded = "Single-writer (one process at a time) … `.beads/embeddeddolt/`"; server = "Connects to a running `dolt sql-server` for multi-client access", config key `dolt.mode: server`, `BD_DOLT_SERVER_MODE=1`, plus **shared server** ("all projects share a single Dolt server … each project uses its own database") and a credentials file (`~/.config/beads/credentials`, `BEADS_DOLT_PASSWORD`, `BEADS_DOLT_SERVER_TLS`). [Troubleshooting](https://beads.gascity.com/reference/troubleshooting.md) → "For high-concurrency scenarios (multiple agents), server mode (`bd init --server`) handles concurrent access natively via `dolt sql-server`"; a **proxied-server mode** also exists ("Proxied-server commands run against a shared `dolt sql-server`"). [Events Journal](https://beads.gascity.com/reference/events-journal.md) → every committed mutation writes one ordered record **in the same transaction**, off by default (`events-journal` / `BD_EVENTS_JOURNAL=1`), read with `bd events tail --since … --follow`, over HTTP at `GET /v0/beads/events` (cursor required, `limit` 1–10000) and as SSE at `GET /v0/beads/events:watch`, each record carrying `"actor"`. [bd audit](https://beads.gascity.com/cli-reference/audit.md) → `.beads/interactions.jsonl`, append-only. **Support:** direct evidence. **Confidence:** high for the docs as fetched (they are `main`, not the version this repo pins — see Missing evidence).

**Claim:** Concurrent humans are *not* thereby made safe: the owner repo's own concurrency design doc records lost-update exposure on the same cell and an unresolved question about optimistic locking.
**Sources:** [engdocs/design/dolt-concurrency.md](https://cdn.jsdelivr.net/gh/gastownhall/beads@main/engdocs/design/dolt-concurrency.md) via jsDelivr. **Support:** direct evidence (first-party **design doc**, i.e. intent, not a shipped guarantee). **Confidence:** medium-high.

Direct quotes from that doc: isolation is "**repeatable read** (vulnerable to lost updates if two connections read-then-write the same cell)"; the conflict matrix says "Two agents update same field of same bead → **Yes** [conflict] → **Last writer wins (updated_at)**"; "The main risk is concurrent status updates (e.g., one agent closes a bead while another also updates it). Mitigation: use optimistic concurrency checks where needed (check expected status before update)"; and among open questions: "**Lost update protection.** … Do we need application-level optimistic locking (e.g., `WHERE updated_at = ? AND status = ?`) for high-contention fields like `status` and `assignee`?" **Interpretation:** the store gives concurrent *writers*; it does not give concurrent *editors* a merge story beyond cell-level auto-merge and last-write-wins. **Researcher inference:** for this repo that is acceptable for the graph (edges, labels, triage moves are discrete commands), but the two high-contention fields the doc names — `status` and `assignee` — are exactly the ones a run and a human both touch (claim vs. triage), so the door should re-read after every write and show the losing edit rather than pretending it landed.

**Claim:** Beads has no user registry, no auth for local writers, and no per-human identity; author and actor are free strings.
**Sources:** [Agent Coordination](https://beads.gascity.com/multi-agent/coordination.md) → "Beads has **no agent registry** — assignees are plain strings. To see which agents are active, group in-progress work by assignee"; `bd assign bd-123 alice`. [Configuration](https://beads.gascity.com/reference/configuration.md) → key `actor` / `--actor` / `BEADS_ACTOR`, default `git config user.name`, "Actor name for audit trail"; "**Actor Identity Resolution** The actor name (used for `created_by` and audit trails) is resolved in this order: 1. `--actor` flag … 4. `git config user.name` 5. `$USER` 6. `"unknown"`". [bd comments](https://beads.gascity.com/cli-reference/comments.md) → `bd comments add [issue-id] [text]` with `-a, --author string  Add author to comment`. [bd comment](https://beads.gascity.com/cli-reference/comment.md) → plain append, `--file`/`--stdin`. [Graph Links](https://beads.gascity.com/core-concepts/graph-links.md) → `replies-to` is "Conversation Threading … ID of parent message (threading)", created for *messages* (`orchestrator mail reply`) or manually by `bd dep add … --type replies-to`; comment listing has no thread model. **Support:** direct evidence. **Confidence:** high.

**Researcher inference:** multiplayer attribution for this repo therefore means *the door passes a name it believes* (`bd comments add <id> --author "<human>"`, `--actor <human>` for audit/`--claim`, `BEADS_ACTOR` for the process). Nothing in the store verifies it, and a `bd` shell on the same machine can write any name. That is a policy layer the surface must own and state plainly, not a store defect.

**Claim:** Today's operator surface is a single-user, single-door Bun server that renders the whole page from one store read and writes comments with **no author flag** — so the store's actor (git user) is the author.
**Sources:** local `tools/operator-ui/serve.ts` (GET `/` returns a server-rendered page from `fetchStore(...)`; `POST /comment` is the only write path; default bind `127.0.0.1:8765`; no session, cookie, or token anywhere in the file) and `tools/operator-ui/comment.ts` (`bd(["comment", id, "--stdin"], text.trim())` — no `--author`). `docs/specs/2026-09-17-operator-surface.md` confirms the intent ("One write door … a single tagged intent"), and the task statement records "author is git user today". **Support:** direct evidence. **Confidence:** high.

**Interpretation:** the two multiplayer defects in the *view* are exactly here — no identity at the door, and a full server-side re-render per request (the "full page reload" pain) that also happens to be the *only* liveness mechanism today (re-read on navigation). A forum-shaped comment pane, per-user attribution, and no-reload re-read are all changes **inside** this file and its neighbours, not in the store.

### 4. Who owns what, store by store (the multiplayer question)

| Question | beads (local Dolt) | Linear (hosted) | GitHub Issues (hosted) | GitLab (hosted/self-managed) |
|---|---|---|---|---|
| **User object** | **None.** Assignee and comment author are free strings; `actor` is a string | `User` with UUIDs; `viewer { id name email }`; app users via `actor=app` ("Agents behave similar to other users in a workspace … @mentioned, delegated issues … create and reply to comments") | Real user accounts; comments embed a full `user` object | Real accounts, project roles |

**Interpretation:** the multiplayer gap in this repo is narrow and nameable. The store owns *state, concurrency, and a per-mutation actor string*; it does not own *identity, authentication, sessions, permissions, or presence*. Everything in that second list must sit in front of the door, and the honest description of the result is "attributed, not authenticated" until a real auth layer is added.

### 5. Recommended assemblies for THIS repo

Constraints honoured in all four: ADR-0001 (beads owns store/graph/frontier), ADR-0006 (closure is per domain), ADR-0007 (surface is a view; executors stay per domain), ADR-0008 (delete refuses dependents/`in_progress`, confirm step), and the spec's refusals. **No fetched evidence justified replacing beads or merging executors** — I looked for a write the door needs that beads lacks (create, intra-domain `blocks`, crossing `relates-to`/`discovered-from`, comment, five triage labels, delete-with-refusal) and found none missing.

#### Assembly A — *Keep + harden the door* (recommended baseline; smallest change that satisfies multiplayer)
- **Store: keep.** Beads stays embedded; nothing about `bd ready`, the derived blocked flag, or the executors changes.
- **View: keep, extend.** React Flow stays the projection; positions stay local. The door grows three things: (1) a session/identity for the human at the browser (a name at minimum, a shared secret at most), (2) that name stamped on every write (`--author` for comments, `--actor` for audit and `--claim`), (3) write-then-**re-read** without a full page reload, plus a comments pane shaped like a conversation over the flat `bd comments` list.
- **Execution: keep.** Three runs, one run lock, allow-list unchanged.
- **What multiplayer means here:** several humans on one page, each with a stamped name, all writing to the same embedded store. **Researcher inference:** this is workable *only* if the door serialises writes (it can — one Bun process, one `bd` invocation at a time) or the store is not embedded (Assembly B). Two simultaneous emits from the same door plus the drain's `bd` process is where the embedded file lock can bite ("Database locked" is a documented symptom, with the documented fix being server mode).
- **Cost:** identity is trust-based; no permissions; a human who can run `bd` is unconstrained.

#### Assembly B — *Keep + switch the store to server mode* (A, plus the store's own multi-writer answer)
- **Store: keep beads, change mode.** `bd init --server` / `dolt.mode: server` (or shared server) so the door, the drain, and a second human's process all write concurrently; note the documented side effects: `.beads/dolt/` instead of `.beads/embeddeddolt/`, auto-commit defaults off in server mode ("Firing `DOLT_COMMIT` after every write under concurrent load causes 'database is read only' errors"), and connection credentials become deployment state (credentials file, TLS flag). Migration both ways via `bd backup` is documented.
- **View: as A**, but the door can now be more than one process, so identity must be per request rather than per process (`--actor` per write rather than `BEADS_ACTOR` per server).
- **Execution: keep.** Workers keep `BD_READONLY=1`; the run lock still serialises starts.
- **Risk to check before adopting:** this repo's store resolution is `store: <bd>` in `.scratch/beads-dag.yaml` plus `bd` on PATH (`docs/agents/issue-tracker.md`), and bd-board's README shows the mode-aware resolution idiom (`bd where --json`) — the pack's preflight/`bd context` behaviour under server mode is unverified here.

#### Assembly C — *Let the store's own HTTP surface carry read + liveness; keep policy in front* (conditional)
- **Store: keep.** Additionally use `bd serve` (documented first-party inside the events-journal page: `GET /v0/beads/issues`, `GET /v0/beads/context` capabilities, `GET /v0/beads/events`, SSE `GET /v0/beads/events:watch`) as the store's read/liveness endpoint, replacing our hand-rolled poll.
- **View: keep the policy door.** Because `bd serve`'s auth is **one shared token for the whole surface** (and loopback-only unless `--allow-non-loopback` is opted into), and because its write endpoints cannot know this repo's rules (no cross-domain `blocks`, triage-only labels, no `closed`), the tagged intent door stays the *only* write path and fronts it.
- **Execution: keep.**
- **Conditional:** I found no dedicated `bd serve` CLI page in the fetched docs index (`llms.txt`), no `docs/cli-reference/serve.md` in the repo file listing at `main`, and no `serve` entry in the site sitemap — and this repo's tracker doc records measurements "On bd 1.2.2", a different version from the docs I fetched. **Do not adopt C before confirming `bd serve` exists in the installed binary and that its write endpoint set is what we'd front.**

#### Assembly D — *Replace the rendering with a community Beads UI; keep beads and the policy door*
- **Store: keep.** **View: replace the DIY page's rendering** with a community project's canvas (best fits: **Scotty** — React Flow graph, comments composer, `bd`-only adapter, MIT; or **bd-board**, whose mode-aware `bd where --json` resolution is the cleanest adapter I saw; **BeadSpec** if a desktop DAG editor is wanted but *not* its direct-Dolt read path).
- **Mandatory guard:** their UIs write `bd` themselves (Scotty: "the app adds zero new persisted schema"; bd-board: create/edit/delete enabled by default). Pointing one at this store would bypass the refusals the door exists for (`closed`, `reading:`, non-triage labels, cross-domain `blocks`, `parent-child`, delete-with-dependents). So: reuse **rendering and adapter only**, keep `applyOperatorAction` as the only write path, and strip/disable their extra model (`deferred` backlog column, `archived` label, UI close, allowlist-based human/agent badges).
- **Execution: keep.**

#### Rejected for this repo (named, with the reason)
- **Replace beads with a hosted tracker** (Linear / GitHub Issues / GitLab / Plane): they own users, auth, permissions and threaded comments — genuinely better multiplayer plumbing — but they replace `bd ready`, Dolt, hash ids, the domains, and the five triage labels. The test the task sets (cite a write beads cannot do) fails: **no such write was found.** ADR-0001 stands.
- **A coordination server as the graph** (BeadHub/aweb): its own "tasks, roles, locks, claims, presence" would be a second claim store beside beads — ADR-0001's exact prohibition. If ever used, restrict it to human/agent **presence and mail**, and say so in the ADR.
- **A CRDT (Yjs) for the graph**: a second graph (ADR-0007). Allowed only for view-only state.
- **BeadBoard / Foolery as the surface**: both bundle an execution runtime and (BeadBoard) an agent registry — the picture would run, and the three executors would be shadowed.

### 6. Components that would replace the DIY React Flow operator-ui (view) vs components that would replace beads (store)

**Can replace the view (with the policy door kept):** Scotty, bd-board, beads-ui, BeadSpec, Beadazzle, Beads Dashboard / beads-web / Beadbox / Beadster / beads.nvim / vscode-beads (all via beads' own [community-tools](https://cdn.jsdelivr.net/gh/gastownhall/beads@main/docs/community-tools.md) catalogue), React Flow itself, and (for sync only) Yjs.
**Would replace beads (store), and are therefore out of scope unless ADR-0001 is re-opened:** Linear, GitHub Issues, GitLab, Plane's work-item store; Airflow/Prefect DAGs occupy the *execution* slot, which ADR-0007 also closes.

**Interpretation of the field:** the community Beads ecosystem is broad on *rendering* and thin on *multiplayer*: every web UI I fetched is local-first, several explicitly single-user (Scotty), and **none documents a user model, login, or per-user permissions**. So the ecosystem can supply the panel and the canvas; it cannot supply the identity layer this new requirement asks for. That layer is small and repo-specific, and it lives at the door.
