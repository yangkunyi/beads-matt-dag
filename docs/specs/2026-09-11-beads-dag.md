# Beads-backed drain — Spec

**Status:** ready-for-agent. (The local-markdown tracker has no label surface, so the triage role is
recorded here rather than applied.)
**Design record:** `docs/specs/2026-09-11-beads-issue-tracker-consensus.md` §10. Authority for every
decision below; where this spec and that document disagree, that document wins and this spec is wrong.
**ADRs:** `docs/adr/0001`–`0004`. **Vocabulary:** `docs/CONTEXT.md`.

---

## Problem Statement

I run unattended implementation work against a Target, and the drain's own record of what it is doing —
which issues exist, what blocks what, which can start, which are in flight, what failed and why — lives
in a directory of markdown files that the drain itself rewrites. So:

- **I cannot ask the store a question.** "What is blocked on this", "what failed and why", "what is in
  flight right now" each require me to write a parser for my own tickets.
- **Dependencies are prose.** They are declared as a text line and a skip rule decides what counts, so a
  malformed line silently makes an issue unstartable — or startable while its blocker is unfinished.
- **"What can start" is a directory scan**, recomputed from scratch every cycle, and it disagrees with
  disk the moment anything writes out of band.
- **The status value is written by the same code that rewrites the file**, so a crash mid-merge leaves a
  status describing an *intent* ("MERGING") rather than a fact, and nothing checks it against git.
- **There is no history.** I can see the current line, not how it got there, and the transitions that
  matter — failed then retried, merged after a conflict — are exactly the ones I need later.
- **Failed work has no chosen policy.** One runner re-picks a failure inside the same run it failed in;
  the other hides it until a human edits the file. Both were accidents of implementation, not decisions.
- **Nothing stops a second process from working the same ticket**, and the two runners that exist are
  kept apart by convention alone.

## Solution

I point the drain at a Target whose issues live in a store. The store owns each issue's status, its
blocking edges, and the answer to "what can start"; git keeps owning the code and the fact that a merge
landed. The drain asks the store for eligible work, claims the whole batch it is about to run in one
transaction, runs the implementer in a worktree, merges into Main, and **only then** records the
outcome — so a recorded success always has its merge commit behind it, and a record that runs ahead of
the merge is impossible rather than merely unlikely. Work left behind by a crashed run is reconciled at
the start of the next drain by reading git. An issue that failed is invisible to the drain that failed
it and visible to the next one, because it is simply `open` again. Abandoning an issue is a label, so it
can never release the work that was waiting on it.

## User Stories

**The operator**

1. As an operator, I want the drain to ask the store what can start, so that I never write a parser for
   my own issue files again.
2. As an operator, I want blocked-ness derived by the store from declared edges, so that a malformed
   line cannot silently hide an issue from the frontier.
3. As an operator, I want a dependency between any two issues to need no naming convention, so that
   publishing never depends on me remembering a scoping rule.
4. As an operator, I want the drain to claim the batch it is about to run atomically, so that two
   workers can never start the same issue.
5. As an operator, I want the number of issues a drain starts to respect the configured concurrency, so
   that a large backlog is not launched at once.
6. As an operator, I want leftover work from a crashed run reconciled at the start of the next run, so
   that I never hand-repair state.
7. As an operator, I want a merge that landed but was never recorded to be recorded, so that finished
   work is not repeated.
8. As an operator, I want a merge that never landed to be recorded as a failed attempt with a reason,
   so that the next drain retries it knowingly.
9. As an operator, I want an issue that failed to be invisible to the drain that failed it and visible to
   the next one, so that a failure cannot loop inside a single run and cannot be forgotten either.
10. As an operator, I want a recorded success to always have a merge commit behind it, so that the store
    cannot claim work that is not in Main.
11. As an operator, I want to read an issue's transition history from the store, so that I can explain
    how it reached its current state.
12. As an operator, I want a failure's reason recorded, so that I know what happened before retrying.
13. As an operator, I want to park an issue out of the frontier without closing it, so that I can stop
    work on it without pretending it is done.
14. As an operator, I want abandoning an issue to never release the work that was waiting on it, so that
    downstream work is never built against a dependency that was not delivered.
15. As an operator, I want the store to answer "what is blocked" and "what is in flight" directly, so
    that the drain-end steps report from the same source the drain acted on.
16. As an operator, I want a preflight before any work starts, so that a missing or unreachable store
    fails the run before it touches a worktree.
17. As an operator, I want blocked-ness recomputed when a drain opens, so that edits made outside the
    drain cannot leave a lie behind.
18. As an operator, I want a documented way to back the store up, so that its being the only record of
    issue state is not a single point of loss.
19. As an operator, I want the drain to say why each eligible-looking issue was not picked, so that
    "nothing happened" is explainable rather than mysterious.
20. As an operator, I want the concurrency cap to be a config value, so that I can run a serial drain
    when the Target needs one.
21. As an operator, I want a drain in which nothing was eligible to be a clean no-op, so that I can run
    it as often as I like.

**The agents**

22. As an implementer agent, I want the body of exactly one issue as a file path, so that I read my whole
    brief with one tool call.
23. As an implementer agent, I want my brief frozen once published, so that it cannot change under me
    mid-run.
24. As an implementer agent, I want to be unable to write issue state, so that I cannot move the frontier
    while I work.
25. As an implementer agent, I want my worktree and branch named from the issue I am on, so that I can
    tell which issue a checkout belongs to.
26. As a conflict agent, I want to be started only when a merge actually conflicted, so that I am not run
    for work that merged cleanly.
27. As a conflict agent, I want to run inside the same issue's execution as the implementer, so that a
    conflict needs no separate workflow and no state of its own.
28. As a reviewer agent, I want to review the range the drain actually merged, so that I review what
    landed rather than what was planned.

**The maintainer**

29. As a maintainer, I want one module to be the only place that talks to the store, so that a store
    change has exactly one home.
30. As a maintainer, I want the workflow definition checked against the scripts it names, so that a
    renamed node or a dropped input fails a test instead of a run.
31. As a maintainer, I want the tests to run against a real store and a real git repository in a temp
    directory, so that a passing test means something about the real thing.
32. As a maintainer, I want the tests to fail loudly when the store binary is missing, so that a green
    run never means "skipped".
33. As a maintainer, I want one seam — the node protocol — so that the same surface the runner drives is
    the surface the tests drive.
34. As a maintainer, I want the node graph to be one drain workflow plus one per-issue executor, so that
    a whole run can be read in one place.
35. As a maintainer, I want the four-state vocabulary to be small enough to hold in my head, so that
    "what does this status mean" is never a lookup.

**The tracker's other readers**

36. As a triage human, I want the gate label to be the only thing that admits an issue to the frontier,
    so that releasing work is one visible act.
37. As a triage human, I want publication to apply that label itself, so that an unattended drain needs
    no human step to keep running.
38. As a repo owner, I want the store ignored by git, so that a runtime database never lands in a commit.
39. As a repo owner, I want the bead's identifier to appear nowhere in git, so that the store can be
    restored or rewritten without invalidating the code's history.

## Implementation Decisions

**The store is the state.** An issue has one of three statuses, all the store's own: `open`,
`in_progress`, `closed`. A failed attempt is an **event, not a status**: it records its reason as a
comment and puts the issue back to `open`, so the retry channel is `bd ready` itself and nothing has to
be registered in the store to make failure expressible. Blocked-ness is derived by the store from the
edges; readiness is `open` and not blocked. Merging and conflict resolution are steps inside a running
issue, not statuses — the worktree's own git state records whether a merge is under way. This is
ADR-0003, and it is the whole reason the drain no longer needs a state for each orchestration step.
What the store therefore cannot answer in one query is "what failed": that is the drain-end report's
job, and §10.3 of the design record says so.

**One module owns the store.** A single module is the only place that shells out to the store: eligible
query, batch claim, mark in-progress, close-as-merged, record-failed-attempt, handle lookup,
history read, blocked-ness recompute, preflight, backup push. Everything else in the pack calls it.
No other module builds a store command.

**The frontier is the store's answer, minus what only this run knows.**

```
candidates    = ready issues − decision-type issues − issues without the gate label
                − issues already attempted by this drain
claimed       = first `concurrency` of candidates, claimed in one transaction
```

The store cannot express that last subtraction, so the drain composes it, and — because the store cannot
explain that exclusion either — the pick step emits its own per-issue exclusion reason into the run's
artifacts. An issue that failed earlier needs no special handling: it is `open` again, so `bd ready`
already returns it, and a drain will work exactly what the store lists.

**Two metadata keys join the store to git.** Each issue carries `handle` (`<feature>/<NN>`, the
human-readable legacy identifier) and `slug`. Branch name, worktree name, the body's path and the merge
commit's subject are all derived from those two facts. Nothing globs the filesystem and nothing guesses
between candidates, and **the bead's own id never appears in git** — so the merge-commit lookup that
makes a merge idempotent (ADR-0029) is unchanged by the migration.

**The issue body is a file, frozen once published.** The drain reads it by path from the two metadata
keys and hands that path to the implementer. The drain never writes it; state lives in the store.
Keeping the two apart is a partition, not a double-write: they share no field. So the published body is
the handle and the prose and nothing else — the `Status:` line the predecessor's tracker wrote into every
issue file is not part of it, and no status the store already holds is repeated there (ADR-0005).

**Merge before stamp (ADR-0002).** The merge into Main happens under the Main-write lock; the status
write happens after it, outside the lock, in the store's own transaction. So `closed` implies the merge
commit exists, and the dangerous interleaving — a state claiming success while Main lacks the commit —
cannot occur. The other interleaving (merged, still in progress) is repaired by the next drain's
reconcile step, which reads git rather than the store.

**Two transitions, one retry loop, one repair.** `open → in_progress` (the claim) and
`in_progress → closed` (after the merge lands); a failed attempt goes back to `open` with its reason
attached as a comment. Repair, at the start of a drain, resolves to one of those two: an issue left in
progress whose branch has a merge commit on Main becomes closed; otherwise it goes back to `open` with
the reason recorded. The Blocked→Ready stamp and the in-flight statuses of the predecessor are gone.

**Retry policy.** A failed attempt is not started again by the drain that made it; the next drain may
start it, because it is `open` again. The cap is per-run and lives in the run's artifacts, not in the
store.

**Closure never crosses domains (ADR-0004).** Only the drain closes an issue, and only to mean the work
is in Main. A failed attempt leaves its issue `open`, never closed — its dependents stay blocked until
the work really lands. Abandoning an issue is a label, and it must not close it,
because closing a blocker releases its dependents whatever the reason. An implementation issue may
therefore only be blocked by another implementation issue; decision issues are a separate domain whose
closure means "the question is answered".

**Decision issues are excluded structurally**, by issue type — never by enumerating a label per flavour,
so a new flavour of question cannot leak into a drain by omission.

**The gate label is the frontier's gate, and publication applies it.** An issue without it is not a
candidate; moving an issue back to a triage state is how an operator brakes one, and "waiting on a human
answer" is one of those states. This keeps an unattended drain running without making the labels
decorative.

**The drain's opening step does four things**, because it is already the always-run node: preflight (the
store binary and store are present, and it fails loudly if not), recompute blocked-ness (the freshness
the old rebuild-every-cycle scan used to provide), reconcile leftovers, and record the base of the range
the drain-end review will read.

**The per-issue executor is one node.** Implement, integrate Main into the worktree, merge; if that
merge conflicts, run the conflict agent in the same execution and merge again. This removes the
predecessor's second workflow, its `returns:` declaration and its output-token gate, whose only purpose
was to give a skipped node a terminal state. The node's timeout must cover both agent turns.

**The executor gates before it merges.** The Target's configured `verify` command runs in the issue's
worktree on the tree that would be merged — after the implementer's turn and again after a conflict turn —
immediately before each settle. Red is an ordinary failed attempt (the reason as a comment, the issue back
to `open`, nothing merged); green lets the settle proceed unchanged. The command comes from the Target's
config and never from an issue body, and it is deterministic: no session, no model, no store field. A
dirty worktree is committed as one checkpoint first, so the gate's subject and the merge's subject are the
same tree, and the same checkpoint runs before the resume path's integration, so a killed turn's dirty
tree cannot make git refuse the merge and lock the issue out before any agent runs.

**The Main-write lock guards git, not the store** (ADR-0002). Every function that writes Main keeps
asserting that the lock is held and the callers keep opening the transaction around a whole compound
step, exactly as today; what changes is that the store write is no longer inside it.

**Workers are read-only against the store**, by the store's own read-only mode in the environment the
drain hands to agent subprocesses, so that the mechanism does not depend on a prompt.

**Config.** Concurrency, model, thinking level and runner keep their current meanings. The store binary
is resolved with a config override first, then from the environment, and a run that cannot resolve it
fails at preflight rather than at the first issue. `verify` is the Target's pre-merge gate — one shell
command, empty meaning the Target has none — and `verifyTimeoutMs` bounds one gate run, so the execute
node's own timeout has to cover two agent turns and two gate runs.

## Testing Decisions

**What makes a good test here.** A test drives one node the way the runner drives it — target directory
as the working directory, inputs in the environment, one token on stdout, exit status — and then asserts
only observable state: the store's statuses, edges and assignee, and git's branches, worktrees, merge
commits and clean Main. No test calls an internal function to check an intermediate value, and no test
asserts on the shape of an artifact file except where the artifact *is* the contract (the pick step's
exclusion report and the drain-end review base).

**The seam — one, and it is the highest one available.** The node protocol *is* the surface the runner
uses, so behaviour tests drive node scripts rather than reimplementing them. Nothing above it gets a
second seam: the workflow definition is covered by the existing text-level contract test (which
cross-checks the definition against the scripts it names — folder resolution, timeout versus each role's
wall clock, input names, dependency references), plus one real end-to-end run of the drain against a
throwaway target, run once per release as an acceptance rather than as part of the suite.

**Modules under test.** The drain's opening step, the pick step, and the per-issue executor, plus the
drain-end review and summary nodes through the fake agent they already take. The store module is
exercised through those nodes rather than unit-tested directly; where a store behaviour needs pinning
(a claim that rolls back, an issue that never appears as ready), it is pinned by a node-level test that
observes the same behaviour a run would.

**Fixture and prior art.** The existing temp-target fixture is the prior art and keeps its shape: a real
git repository with a seed commit, a temp artifacts directory, real worktrees, a stub agent that records
the options it was handed, and expectations written as named assertions. It gains one step — initialising
a real store in the target — which makes the whole suite depend on the store binary being present. That
dependency must fail loudly: no skipping, no fallback to a fake store. The predecessor's repro-script
suite is the model for the new one; its file-level topics carry over (drain loop, begin/resume, leftover
reconciliation in both directions, pick, settle, config, roles, review, summary, workflow contract) and
its status-parsing and status-line topics are deleted with the mechanisms they tested.

**Acceptance.** Four checks in a throwaway lab, never against a live target: the frontier excludes
decision issues and refuses anything without the gate label; an issue whose attempt failed is not
retried inside its drain and is retried by the next one; closure never crosses domains; and a kill
between merge and status write leaves state the repair path fixes.

## Out of Scope

- The tracker template in the skills repository and the identifier rule it hardcodes — both are edits
  outside this repo and each needs its own approval.
- Using beads as *this* repository's own tracker. This repo stays on the local-markdown convention: it
  is where the beads flow is designed, not a place the flow already runs.
- Migrating an existing target's ticket files into a store.
- The retired CLI's code.
- Automating the store's remote backup (the mechanism is in scope; a scheduler is not).
- Multi-machine store federation.
- Changing what the drain-end review and summary say — only where they read it from.

## Further Notes

- The predecessor pack stays frozen and installed until this one passes acceptance; the live drain on
  the other target must not be touched while it is running.
- Reference sizes: a store measures at roughly 75 KB per issue including history, so a 99-issue target
  is a few megabytes — size is not a constraint on keeping full history.
- The store's gitignore is written by the store's own init and ignores the database plus runtime files;
  the issue body files are tracked, because they are the part of an issue that belongs to git.
- A merge that landed but was never recorded is caught by the opening reconcile, which runs before
  pick: such an issue is still `in_progress`, so it is not a candidate, and the repair closes it. Pick
  therefore makes no git check of its own.
- Anything this spec and the design record disagree on is a bug in this spec.
